# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal Azure homelab infrastructure-as-code: pure Terraform + GitHub Actions. No application code, no tests, no Makefile. Six independent root modules, each with its own remote state — five in the CI pipeline, plus `infra/identity`, which is bootstrapped locally and has no workflow.

## Modules and deployment order

Deploy in this order — later modules find earlier ones' resources **by name via data sources** (there is no `terraform_remote_state` linkage), so renames break downstream modules silently:

0. `infra/identity` — **one-time local bootstrap, outside the five-module CI pipeline.** UAMI `homelab-github-actions-identity` in its own `homelab-identity-rg` + two GitHub OIDC federated credentials (subjects `repo:114snehasish/homelab:ref:refs/heads/main` and `:pull_request`). It cannot deploy itself via CI — the credential it would need is the thing it creates — so there is deliberately no `deploy-identity.yml`; runbook in `docs/oidc_bootstrap.md`. Since E02.3 (#35), **all CI depends on it**: every workflow authenticates as this UAMI, so recreating it (it carries `prevent_destroy = true`) mints a new `client_id` and breaks every run until the repo variables are updated. As of E02.2 (#34) it also holds three role assignments and nothing more: `Contributor` on `homelab-rg`, `Storage Blob Data Contributor` on the `tfstate` **container** (not the storage account — an account-scoped role carries `listKeys`, and that key is a bearer credential for every container in it), and `Reader` on the single `homelab-vm-ssh-key-2` resource that `compute/vm`'s data source reads. Two consequences worth holding onto: RG-scoped Contributor **cannot recreate `homelab-rg`** (a role assignment dies with its scope, and RG creation is a subscription-level write) — recovery is a local apply with the SP; and the blob grant is inert unless Terraform talks to the backend with Entra auth, so any OIDC run must set `ARM_USE_AZUREAD=true` as well as `ARM_USE_OIDC=true`, or `terraform init` dies at `listKeys` before validate. Applying this module needs `roleAssignments/write` (Owner or User Access Administrator) — Contributor alone cannot hand out roles.
1. `infra/network` — `homelab-rg`, VNet 10.0.0.0/16, subnet, NSG
2. `infra/dns` — Azure DNS zone `az.snehasish-chakraborty.com` (root domain `snehasish-chakraborty.com` lives in Cloudflare)
3. `infra/cloudflare` — NS records delegating `az.*` from Cloudflare to Azure DNS
4. `infra/storage` — persistent 20GB data disk (`prevent_destroy = true`)
5. `compute/vm` — disposable VM (`homelab-vm.az.snehasish-chakraborty.com`); attaches the data disk at LUN 10 and registers its own DNS A record

Run `terraform init && terraform plan|apply` inside each module directory. Plans/applies happen both locally and via GitHub Actions — no strict rule.

## Never touch

These pre-exist and are managed **outside this repo** — never import, modify, or destroy:
- RG `do-not-delete` and storage account `listeninfratfstatesa` (the Terraform state backend, container `tfstate`, keys `homelab.<module>.tfstate`)
- SSH public key `homelab-vm-ssh-key-2` in `do-not-delete` (read by data source in `compute/vm`)

Design is "cattle VM, pet disk": destroying/recreating `compute/vm` is routine; the `infra/storage` disk and its data must always survive (cloud-init only formats the disk if unformatted).

## Local setup

- Azure auth: `ARM_*` env vars (`ARM_CLIENT_ID`, `ARM_CLIENT_SECRET`, `ARM_TENANT_ID`, `ARM_SUBSCRIPTION_ID`) from the gitignored root `.env`
- Cloudflare: `TF_VAR_cloudflare_api_token` / `TF_VAR_cloudflare_zone_id`
- `infra/dns`, `infra/cloudflare`, `compute/vm` each need `terraform.tfvars` copied from `terraform.tfvars.example` (gitignored)

## Gotchas

- The NSG SSH rule whitelists the public IP of whatever machine runs plan/apply (fetched live from api.ipify.org) unless `ssh_source_ip` is set — local and CI plans always disagree on this rule.
- cloud-init contract (`compute/vm/cloud-init.yaml`): discovers the data disk at `/dev/disk/azure/scsi1/lun10`, mounts at `/data`. Changing the LUN in Terraform breaks it.
- The NS record name in `infra/cloudflare/main.tf` is `var.azure_dns_zone_name` (the full delegated zone FQDN, e.g. `az.snehasish-chakraborty.com`) — Cloudflare provider v5 (`cloudflare_dns_record`) matches DNS records by FQDN, so a bare `az` label drifts every plan. Keep it pointed at the Azure DNS zone name being delegated.
- Dependabot-triggered runs (`pull_request` and the branch `push` alike) read **Dependabot secrets**, not Actions secrets — none are configured, so `CLOUDFLARE_*`/`DNS_ZONE_NAME`/`RESOURCE_GROUP_NAME` interpolate empty and the Terraform job fails before producing a real plan (TFLint/Checkov still pass). A red Terraform check on a fresh Dependabot PR therefore says nothing about the bump itself: push any commit to the PR branch as a maintainer (empty is fine) to re-run CI with real repository secrets — that is how #143–#147 were driven to a real plan. Mirroring the secrets into Settings → Dependabot secrets is the standing fix (tracked in #138, roadmap R17). **E02.3 (#35) changed the likely failure mode and #138 has not been re-tested since:** Azure auth no longer comes from secrets at all (repo variables are readable by Dependabot runs), but Dependabot runs get a read-only `GITHUB_TOKEN`, so the job may now die earlier — unable to mint the OIDC token for `id-token: write` — rather than at backend auth. Treat the exact error on the next Dependabot PR as new information, and don't assume #138 alone will turn the check green.
- The azurerm 4→5 major bump (#143–#147) needed zero code changes: provider blocks are a bare `features {}` and nothing this repo uses was removed in 5.0. One 5.x behavior change to remember: `resource_provider_registrations` now defaults to `"none"`, fine for every resource type already deployed — but a future module using a never-registered resource provider must register it out-of-band (or opt in via the provider block). `infra/identity` is the first module to hit this: `az provider register --namespace Microsoft.ManagedIdentity` is step 0 of its bootstrap runbook, and skipping it fails the apply with an unsupported-API-version error that never mentions registration.
- Azure auth is **keyless OIDC everywhere**, as of E02.3 (#35). Every workflow authenticates as the UAMI from `infra/identity` using repo **variables** `ARM_CLIENT_ID`/`ARM_TENANT_ID`/`ARM_SUBSCRIPTION_ID` (identifiers, not secrets) plus `ARM_USE_OIDC=true` and `ARM_USE_AZUREAD=true`. No workflow references a client secret. This replaced the old `ARM_*` (network/storage/compute) vs `AZURE_*` (dns/cloudflare) secret-name split, which is gone — if you see that split described anywhere else, that doc is stale. The `ARM_*`/`AZURE_*` secrets still *exist* in repo settings, unused, until E02.4 (#36) deletes them and rotates the SP; that is deliberate, so reverting the cutover is a one-commit rollback. Still-live secrets: `DNS_ZONE_NAME`, `RESOURCE_GROUP_NAME`, `CLOUDFLARE_*`, `PUBLIC_REPO_URL`/`PUBLIC_REPO_TOKEN`.
- **Deploy `push:` triggers are pinned to `branches: [main]`, and must stay that way.** A workflow run's OIDC subject is `repo:114snehasish/homelab:ref:refs/heads/<branch>` on push and `...:pull_request` on PR, and only `:ref:refs/heads/main` and `:pull_request` federated credentials exist. So a feature-branch push run can only ever fail at Azure auth. Feature branches get their plan from the `pull_request` trigger. Removing the branch filter re-breaks every feature-branch push; the fix is *not* a wildcard federated credential, which would trust any branch anyone can push. `workflow_dispatch` inherits the ref it is dispatched from, so dispatch from `main` — this is why the gated apply can only be proven after merge.
- Apply gate is uniform (resolved by #28): all five module workflows run plan on push/PR and apply only via manual `workflow_dispatch` with the apply checkbox (default unchecked). No workflow auto-applies on push.
- `deploy.yml` is the overall pipeline: it calls the five `deploy-*.yml` workflows as reusable workflows (`workflow_call`, `secrets: inherit`) in dependency order. Its `apply_terraform` checkbox gates apply in every module job — unchecked = plan-only dry run across all five.
- `destroy.yml` tears down `compute/vm` → `infra/cloudflare` only. It deliberately skips `infra/storage` (the pet disk), `infra/network`, and `infra/dns`: the disk lives inside `homelab-rg`, so destroying the network module would delete (or fail on) the RG holding the disk, and VNet/subnet/NSG/RG stay up since they cost nothing; the DNS zone is a flat ~$0.52/month regardless of usage, so it's not worth tearing down every cycle — destroying it was also the direct cause of recurring plan failures in `infra/cloudflare`/`compute/vm`, which look it up by name via a data source with no tolerance for it being absent (#124). `apply_destroy` unchecked = dry run. Since #153 it is a thin caller of `_terraform.yml` like the five `deploy-*.yml` workflows — two `uses:` jobs whose only difference from a deploy caller is `destroy: true`, with no `runs-on`, `setup-terraform`, `env:` or auth of its own. It therefore inherits the `.terraform-version` pin, `terraform validate` and the per-module `tf-<dir>` concurrency group, and the shared path no longer has to be mirrored into it by hand (which #35 had to do). It is still the only workflow that can delete real infrastructure: keep `apply_destroy` unchecked until you have read the plan.
- Deploy and destroy share `concurrency: homelab-terraform` so they can't interleave. That is workflow-level; each called `_terraform.yml` job additionally takes the `tf-<working_directory>` group that actually leases the module's state blob.
- All five `deploy-*.yml` workflows — plus `destroy.yml` since #153 — are thin wrappers around `.github/workflows/_terraform.yml` (a `workflow_call`-only reusable workflow taking `working_directory`/`apply`/`ssh_source_ip`/`destroy`), each run under a `tf-<working_directory>` concurrency group. `destroy` (default `false`, used only by `destroy.yml`) flips the plan step to `terraform plan -destroy`; it deliberately does **not** get its own apply gate — the plan file is applied by the same `inputs.apply` step either way, so there is one gate to reason about rather than two. It pins the Terraform CLI version from the repo-root `.terraform-version` file and always runs `terraform validate`. As of E02.3 (#35) it has **no per-module conditional steps at all** — auth is one unconditional OIDC step for every module, and the `TF_VAR_rg_name`-for-`infra/dns` workaround is gone (that module's variable was renamed `dns_rg_name`, so it picks up the static `TF_VAR_dns_rg_name` entry the workflow already sets for `compute/vm`). Keep it that way: variable names that mean the same thing across modules belong in the shared `env:` block, and a name that collides should be renamed in the module rather than routed around with an `if:`. Auth is still written via `$GITHUB_ENV` rather than static `env:`, because a static entry silently wins over a later `$GITHUB_ENV` write.
- `oidc-smoke.yml` **was deleted in E02.3 (#35)** — owner's call, once OIDC became the default and its five plan jobs duplicated the `deploy-*.yml` PR plans. Two coverage gaps came with it, and both are real: (1) **nothing now asserts what the CI identity *cannot* do.** The deleted `negative-access` job was the only check proving the UAMI can't read RG `do-not-delete`, can't `listKeys` on the state storage account, and can't see its own resource group — every remaining check proves the identity *can* do something, so a future change that quietly widens the grants goes unnoticed. (2) **A PR touching only `infra/identity/**` runs no Terraform at all** — no `deploy-*.yml` path filter matches it. The `_terraform.yml` half of this gap was closed by #153, which added `.github/workflows/_terraform.yml` to all five deploy workflows' `push`/`pull_request` path filters, so a change to the shared workflow now gets a real plan from every module (and a merge to `main` fires five plan-only runs — no workflow auto-applies on push). If you want the assertions back, they are recoverable verbatim from git history (`git show <pre-#35>:.github/workflows/oidc-smoke.yml`); re-adding them as a scheduled or dispatch-only workflow is the cheap version.
- On a PR that touches `.github/workflows/deploy-*.yml`, **every** push re-triggers all five deploy workflows regardless of what changed: `pull_request` path filters match the PR's entire diff, not just the newest commit. A docs-only commit on such a branch still fires five Terraform plans (plus the smoke run), which is how the state-lock pile-up above was discovered.
- Every caller of `_terraform.yml` must grant at least what `_terraform.yml` declares (`contents: read`, `pull-requests: write`, `id-token: write`) — a called workflow requesting more than its caller has fails the run at **startup**, with zero jobs and no log to read. `actionlint` does not catch it and neither does `lint.yml`; the only signal is a `startup_failure` conclusion on the run.
- `main` is force-mirrored to a public GitHub repo on every push (`mirror.yml`) — treat everything committed as public; never commit tfvars, keys, or `.env`.
- `docs/technical_reference.md` predates the dns/cloudflare modules — update `docs/` when adding or changing modules.
- `lint.yml` (tflint + checkov, both blocking) runs repo-wide on any `.tf` change, separate from the five per-module pipelines. `.tflint.hcl` is a single repo-root config covering all five modules via `tflint --recursive`. Checkov findings that are real but not fixable yet are silenced with an inline `# checkov:skip=<ID>:<reason>` comment placed *inside* the resource block (a comment above the `resource` line is out of the range checkov scans) — not a separate baseline file.

## Conventions

- Azure resource names: `homelab-*` kebab-case; Terraform resource labels: `homelab_*` snake_case; region `southindia`.
- Branches: snake_case topical names, PR into `main` (merge commits).
- Adding a VM: use `compute/vm`, pass the correct `dns_zone_name`. Static DNS records go in `infra/dns/main.tf`; VM A records are managed by the VM module itself.
